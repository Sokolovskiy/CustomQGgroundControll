## Mission Planner comparison

The user reports stable command delivery with Mission Planner. Inspection of
the current official Mission Planner master implementation (not a verified
match to the user's installed version) found material differences:

- setMode sends DO_SET_MODE without requiring an ACK, followed by two SET_MODE
  messages, separated by 10 ms.
- doCommandAsync starts with three retries and a 2000 ms ACK wait, with
  command-specific exceptions. COMPONENT_ARM_DISARM uses a 10000 ms wait;
  ordinary disarm uses param1=0 and param2=0.
- Our v5.1.5 setFlightMode sends DO_SET_MODE for ArduPilot. Mode, relay and
  ARM/DISARM commands are not automatically retried, with a nominal 1200 ms
  ACK wait (500 ms queue polling adds timing quantization).

Source: https://github.com/ArduPilot/MissionPlanner/blob/master/ExtLibs/ArduPilot/Mavlink/MAVLinkInterface.cs

This provides a plausible explanation for apparent Mission Planner robustness
without proving where initial packets are lost. No repeated ARM/DISARM, force
actions, hidden ACK suppression or general queue policy changes are made on
the basis of this comparison. A future mode/relay delivery design must discard
superseded requests, remain tied to the current vehicle/connection, and retain
explicit failure reporting. ARM/DISARM must be considered separately.

## Bounded mode/camera delivery implementation

The custom build now opts absolute DO_SET_MODE selections and Relay2 index 1
OFF/ON into up to three total transmissions with the existing 1200 ms ACK window
per transmission. The 500 ms polling timer means the complete failure window
can approach 4.5 seconds. Other commands, ARM/DISARM, relay Toggle, handler-owned
commands, other relay indices and high-latency links retain their prior policy.
Eligibility is guarded by QGC_CUSTOM_BUILD. The upstream executable is preserved.

A newer selection stops retries of its pending predecessor. Its latest intent
replaces any previously deferred intent, waits until the existing ACK slot
terminates, then is dispatched on the next event-loop turn. It expires if older
than 2000 ms, or if the active vehicle, primary link, communication state or armed
state has changed. Retry sends have the same link/active-vehicle/armed-state
guards. Generation checks discard callbacks superseded during result handling.
Displayed state remains actual telemetry: no mode, relay or armed Fact is assigned
to manufacture success. Superseded requests emit CANCELLED; final failures of
the current request remain visible.

MAVLink ACKs contain command ID, not original parameter values or transaction
IDs. Serializing pending selections and draining the current event-loop batch
reduces misassociation, but cannot distinguish arbitrarily late duplicate ACKs
from earlier transmissions. Accepted ACK is not proof of physical completion;
real telemetry remains authoritative. This is a bounded delivery mitigation,
not proof that the underlying packet-loss cause is solved.

Production changes: src/Vehicle/MavCommandQueue.h and MavCommandQueue.cc. No

## User-approved short ARM/DISARM repeat

On 2026-11-05 the user explicitly approved one repeat after 100 ms with a
250 ms cutoff. This supersedes the earlier unchanged-ARM-policy status above.
Only the custom build, an active ArduPilot vehicle, its default autopilot
component, COMMAND_LONG without custom handlers, param1=0 or 1 and param2-7=0
are eligible. The observed armed state must differ from the requested state.
Disconnected, communication-lost and high-latency links are excluded.

A precise single-shot timer schedules the repeat after the initial dispatch.
Both the timer callback and the final pre-dispatch check enforce a monotonic
elapsed time below 250 ms. At most two transmissions are possible, confirmation
0 then 1. The ordinary 500 ms queue timer cannot send a late repeat: the same
eligibility guard forces its normal terminal failure path after the ACK timeout.
The ACK timeout itself is unchanged and is not restarted by the short repeat.

Each new ARM/DISARM request, even one rejected as already pending, invalidates
the older repeat. Observed armed, active-vehicle, primary-link, communication
state and link-disconnect transitions also invalidate it, including a transition
back before the callback runs. A matching terminal ACK removes the entry;
IN_PROGRESS disables its repeat. Neither denial nor timeout triggers force-arm.
New opposite requests still follow the existing pending-command rejection rule;
they cancel the repeat but are not deferred or silently queued.

The cutoff bounds local dispatch, not arrival at the FC: bytes already handed
to Qt/Windows/Herelink cannot be recalled or given a delivery deadline here.
Only received/processed state and ACK information can cancel a future dispatch.
ACK transaction ambiguity remains as documented above. This mitigation does
not establish the packet-loss root cause or prove hardware reliability. Pre-arm
checks, failsafes, FC parameters and joystick mappings remain unchanged.
